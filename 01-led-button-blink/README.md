# 01 - Button-controlled LED blink (bare metal)

Blinks the on-board LED (LD2) and lets the user button (B1) cycle through three blink speeds. Written in C with my own register definitions for GPIO and RCC, with no HAL and no vendor register headers.

- **Status:** Working
- **Board:** NUCLEO-F446RE (STM32F446RE, Arm Cortex-M4)
- **Language / toolchain:** C (gnu11), STM32CubeIDE, GCC for Arm

---

## 1. Goal and requirements

1. LD2 blinks continuously.
2. Each press of B1 switches to the next speed: slow, medium, fast, then back to slow.
3. A press is never missed, even at the slowest speed.
4. A long press changes the speed only once.

**Constraints I set**
- All hardware access goes through my own register structs and the bit helpers in `bits.h`.
- No HAL, no interrupts, no timers (polling only).

**Out of scope**
- Accurate timing. The delay is a busy-wait loop, so the blink period depends on clock speed and compiler optimization.

## 4. Design

### How it works

The main loop toggles the LED, reads the current delay once, and then counts to that fixed number. On every pass of that counting loop it calls `speed_steps()`, which reads B1 and compares it with the previous reading saved in a `static` variable. If the button went from released to pressed, it advances to the next entry in a `delays[]` array using `(index + 1) % array_size`.

Polling inside the delay means a quick tap is never missed. Copying the delay to `loop_bound` before the loop means a press changes the speed for the **next** blink without cutting the current one short.

### State

| State | Where it lives | Purpose |
|---|---|---|
| Previous button level | `static` in `speed_steps()` | Detect the released-to-pressed edge |
| Current speed index | `static` in `speed_steps()` | Choose the delay |
| Delay values | `static const` array | Slow, medium, fast |

### Key design decisions

| Decision | Alternatives | Why this one |
|---|---|---|
| Toggle on the press edge | Toggle while held; toggle on release | One action per press, and the LED changes at the moment of the press |
| Poll inside the delay loop | Poll once per blink | Does not miss short taps |
| Fix the loop bound before counting | Let the polled value change it mid-delay | Keeps each blink period consistent |
| Array and `% size` | `if / else if` chain | One line to advance; adding a speed means adding one array entry |

## 8. Results and limitations

- Works as specified on my board.
- The delay is a busy-wait. The blink period depends on the clock speed and the optimization level, and the CPU can do nothing else while it waits.
- A hardware timer is the proper fix and is on the roadmap.

## 9. What went wrong (debugging log)

| Symptom | Cause | Fix | What I learned |
|---|---|---|---|
| Build failed with a duplicate member name | Two reserved members in the RCC struct were both named `RESERVED8` | Renamed the second one | Struct member names must be unique |
| LED would stay dark (caught in review) | Passed the pin number (5) as the `MODER` shift instead of the bit position (10) | Used `pin * 2` | A pin number and a bit position are different things |
| LED would not follow the button (caught in review) | Copied the whole `IDR` into `ODR`, but the button is bit 13 and the LED is bit 5 | Read one bit with `test_bit`, update one bit of `ODR` | Operate on single bits, not whole registers |
| LED toggled on release and blocked | Waited in a `while` loop for the release | Saved the previous state and compared | Edge detection needs the previous value, and waiting blocks the program |
| Speed changed erratically on one press | Saved button state was never updated | Update it on every pass, outside the `if` | Update remembered state every pass |
| Taps could be missed | Read the button only once per blink | Poll inside the delay loop | Polling must happen often enough |
| Blink period glitched when pressing | Loop bound changed during the loop | Copy the delay before the loop starts | Don't move the finish line while running |

## 10. What I would do next

- Replace the busy-wait with a hardware timer.
- Print status over UART (USART2 on the ST-LINK virtual COM port).
- Replace polling with an interrupt on the button.
